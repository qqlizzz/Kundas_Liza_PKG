Цель работы
Изучить цветовые модели RGB, CMYK и HLS, освоить математические преобразования между ними, а также разработать приложение, наглядно демонстрирующее эти преобразования в интерактивном режиме.

Задачи работы
Изучить теоретические основы аддитивной модели RGB, субтрактивной модели CMYK и цилиндрической модели HLS.
Изучить математические формулы взаимного перевода между RGB, CMYK и HLS.
Изучить алгоритмы цветоделения UCR (Under Color Removal) и GCR (Gray Component Replacement).
Изучить стратегии обработки выхода за границы цветового охвата — Clipping и Scaling.
Изучить понятие цветового охвата и цветовой график МКО.
Изучить архитектурный паттерн MVVM и принципы разделения кода на слои.
Реализовать все математические преобразования вручную, без использования сторонних библиотек конвертации.
Разработать приложение с архитектурой MVVM, разделив код на слои Model, ViewModel и View.
Реализовать три способа задания цвета: ползунки, поля ввода и палитру в стиле графических редакторов.
Обеспечить автоматический пересчёт всех трёх моделей при изменении любой координаты.
Добавить ненавязчивое предупреждение о выходе цвета за границы RGB.
Написать автоматические микро-тесты для проверки корректности математики.
Собрать приложение в EXE-файл для Windows и разместить исходный код на GitHub.

Актуальность
Понимание цветовых моделей и их взаимных преобразований — базовый навык для специалистов в областях:
Веб-разработка и UI/UX-дизайн — работа в RGB, HEX, HLS.
Полиграфия и предпечатная подготовка — конвертация в CMYK с учётом цветового охвата.
Разработка графических редакторов — реализация цветовых пикеров и алгоритмов gamut mapping.
Компьютерное зрение — корректная работа с цветом на разных устройствах.

Проблема цветового охвата особенно актуальна: пользователи часто сталкиваются с тем, что яркие цвета на экране выглядят тускло на печати. Понимание причин этого явления и способов его смягчения (Clipping, Scaling) — важная практическая задача.

Ход работы
1. Изучение теоретического материала
Начал с истории возникновения цветовых моделей. Цветовое зрение исследовали экспериментально: образец освещали тремя прожекторами — красным, зелёным и синим — и подбором интенсивностей добивались совпадения с образцом. Оказалось, что часть цветов так получить нельзя: приходится «вычитать» свет, что математически означает отрицательные коэффициенты. Чтобы уйти от них, МКО линейным преобразованием ввела координаты XYZ и построила диаграмму цветности xy — подковообразный локус спектральных цветов. Именно на этом графике видно, что охват RGB покрывает лишь часть видимых цветов.

Далее разобрался с моделью CMYK: принтер наносит краску на бумагу и цвет получается вычитанием из белого. Смесь C + M + Y должна давать чёрный, но на практике получается грязно-коричневый, поэтому добавляют четвёртую чёрную краску K. Модель HLS оказалась самой интуитивной: цвет задаётся тоном на цветовом круге, светлотой и насыщенностью — именно так думает дизайнер.

2. Проектирование архитектуры
Приложение построено по паттерну MVVM — модификации MVC, хорошо подходящей для GUI. Разделил код на три независимых слоя:

Model (model.py) — чистая математика преобразований. Никаких import tkinter, только числа и формулы.

ViewModel (viewmodel.py) — хранит текущее состояние цвета во всех трёх моделях, принимает команды от View, зовёт Model, отдаёт результат обратно.

View (view.py) — только интерфейс на tkinter, без математики.

Такое разделение позволяет тестировать математику в отрыве от интерфейса (tests.py) и при необходимости заменить GUI, не переписывая формулы.

3. Реализация преобразований
Все формулы реализованы вручную, без colorsys и других библиотек:

RGB → CMYK: K = 1 - max(R, G, B), потом C = (1 - R - K) / (1 - K) и так далее. Отдельная проверка на K = 1, чтобы избежать деления на ноль.

CMYK → RGB: однозначная формула R = 255 * (1 - C) * (1 - K).

RGB → HLS: светлота через (max + min) / 2, насыщенность двойной формулой для тёмных и светлых цветов, оттенок — три ветки по доминирующему каналу.

HLS → RGB: вспомогательная функция _hue_to_rgb и круговой сдвиг на 120° между каналами.

UCR: K = K_max, вычитаем из CMY с делением на (1 - K).

GCR: K = min(C, M, Y), вычитаем без деления.

4. Реализация интерфейса
Три способа задать цвет:

Ползунки — 10 штук: 3 RGB, 4 CMYK, 3 HLS. Каждый связан с полем ввода через общую DoubleVar.

Поля ввода — рядом с каждым ползунком. По Enter применяется значение.

Палитра — отдельное окно в стиле графических редакторов: большой 2D-выбор цвета (насыщенность × светлота), радужная полоса оттенка, полоса светлоты, сетка быстрых пресетов.

Внизу левой панели — блок «Результат» с превью, HEX, RGB и кнопками Сохранить / Загрузить для избранного.

5. Автоматический пересчёт
Ключевой метод — _update_from_rgb во ViewModel. Любое действие пользователя приводит вход к RGB и вызывает его. Метод:

Применяет стратегию выхода за границы (Clipping или Scaling).

Формирует предупреждение, если был выход.

Пересчитывает CMYK по выбранному алгоритму (UCR/GCR).

Пересчитывает HLS.

После этого View вызывает refresh(), который синхронизирует все 10 переменных и обновляет интерфейс.

6. Проблемы и их решения
Проблема 1. Палитра тормозила при движении мыши.

Первая версия перерисовывала картинку 320×220 на каждое движение — это 70 400 вызовов hls_to_rgb. Решение: рисовать блоками 4×4 вместо 2×2 (в 4 раза меньше вычислений), кэшировать по оттенку H (если H не изменился — картинку не перерисовывать), использовать after_idle для отложенной перерисовки полосы светлоты, а маркер вынести в отдельный тег, чтобы он двигался, не трогая градиент.

Проблема 2. Кнопки палитры все становились одного цвета.

Классическая ошибка Python с замыканиями. В цикле for лямбда захватывает переменную, а не её значение — все 60 кнопок получали последние значения из цикла. Решение: параметры по умолчанию lambda rr=r, gg=g, bb=b: ... захватывают текущее значение в момент создания.

Проблема 3. Ctrl+C не копировал HEX.

Поле HEX было в состоянии readonly, а Tk в этом режиме игнорирует клавиатурные события. Решение: привязал Control-c, Control-C и Control-Insert к своему обработчику _copy_hex, который вручную кладёт текст в буфер обмена через clipboard_append. В конце обработчика — return "break", чтобы Tk не пытался обработать событие ещё раз.

Проблема 4. Все ползунки одного цвета терялись на тёмном фоне.

Первая версия делала troughcolor (длинную дорожку) цветной, а ручку — тоже цветной. Ручка сливалась. Решение: ручку (bg) зафиксировал в светло-сером KNOB, а troughcolor перекрашиваю динамически в текущий цвет. Так ручка видна всегда, а дорожка показывает результат.

Проблема 5. Тема ttk на Windows не поддавалась стилизации.

Стандартная тема vista жёстко задаёт цвета виджетов. Решение: переключился на кроссплатформенную clam, в которой цвета настраиваются через Style().configure(...).

7. Автоматические тесты
В tests.py — 12 тестов на базе unittest:

test_rgb_to_cmyk_red — проверка чистого красного.

test_cmyk_to_rgb_red — обратное преобразование.

test_rgb_to_hls_red — H = 0, L = 0.5, S = 1.

test_hls_to_rgb_red — обратное.

test_rgb_to_cmyk_white, test_rgb_to_cmyk_black — граничные случаи.

test_rgb_to_hls_green, test_rgb_to_hls_blue — проверка оттенков.

test_ucr_black, test_gcr_black, test_gcr_gray — цветоделение.

Сравнение с точностью до 4 знаков через assertAlmostEqual, потому что числа с плавающей точкой не всегда точны.

Вывод
В ходе лабораторной работы я прошла путь от теоретического изучения цветовых моделей до полноценного интерактивного приложения. Начала с истории цветового зрения: узнала, как эксперименты с тремя прожекторами привели к идее трихроматической модели, почему часть цветов нельзя получить без «отрицательных» коэффициентов, и как МКО ввела систему XYZ, чтобы уйти от этих отрицательных значений. От XYZ перешла к диаграмме цветности — тому самому подковообразному графику, на котором наглядно видно, что охват RGB — лишь часть видимых человеком цветов, а значит, при переводах неизбежны ситуации выхода за границы.

Разобралась в трёх моделях, которые нужны для моей цепочки: RGB — аддитивная, для экранов; CMYK — субтрактивная, для печати; HLS — цилиндрическая, интуитивная для человека. Поняла, почему в CMYK нужен четвёртый канал: смесь CMY не даёт чистого чёрного, и его приходится добавлять отдельно. Изучила два алгоритма цветоделения — UCR и GCR. Убедилась, что один и тот же визуальный серый можно получить по-разному, и задача алгоритмов — выбрать оптимальный рецепт: UCR экономит краску в тенях, GCR — во всём диапазоне.

Реализовала все формулы вручную — без colorsys и других библиотек. Писала каждую строчку, осознанно разбирая каждый шаг: где нужна проверка на деление на ноль, где двойная формула для светлого и тёмного, где круговой сдвиг на 120° между каналами.

Спроектировала архитектуру по паттерну MVVM: Model — чистая математика, ViewModel — логика синхронизации, View — интерфейс. Это решение я считаю одним из главных в работе: без него код быстро превратился бы в монолит, где формулы переплетены с кнопками, а тесты невозможно запустить без GUI. С MVVM же математика тестируется в отрыве, а интерфейс можно переписать, не тронув формулы.

Столкнулась с рядом практических проблем и решила их. Палитра тормозила — оптимизировала через блоки 4×4, кэш по оттенку и отложенную перерисовку. Кнопки палитры все становились одного цвета — разобралась с замыканиями в Python и применила параметры по умолчанию в лямбдах. Ctrl+C не копировал HEX — добавила ручной обработчик буфера обмена. Ручки ползунков терялись на фоне — зафиксировала их цвет, оставив цветной только дорожку. Тема ttk не поддавалась стилизации — перешла на clam. Каждая из этих проблем дала понимание, как работает Tk и Python изнутри.

Написала 12 автотестов на unittest, покрывающих чистые цвета, граничные случаи и оба алгоритма цветоделения. Тесты стали для меня страховкой: при изменении формул я сразу видела, что что-то сломалось.

Собрала приложение в EXE через PyInstaller и разместила на GitHub с README и отчётом. Это научило меня оформлять результат — не только писать код, но и делать его доступным для других.

Итог: я не только изучила теорию цветовых моделей и реализовала преобразования, но и получила опыт разработки полноценного GUI-приложения с правильной архитектурой, тестами, оптимизацией и документацией. Все задачи лабораторной выполнены, приложение работает, код на GitHub, EXE готов к сдаче.
